# 物理层设计说明

> 本文记录 2026-11-03 的一次设计转向：**把「共鸣规则」改成「物理层涌现」**。
> 正式条款见 `GameDesign.md` §5 与 `Ghosts.md`。
> 这篇是决策记录与实现指引，解释「为什么这么改」与「代码要怎么变」。

---

## 1. 转向的起因

原策划案 §5 是一套「三层共鸣结构」：端口 → 反射 → 场域，外加一张「共鸣规则实例」表（条件 + 效果 + 代价）。

这套写法的问题：

- 每加一条共鸣，就要往规则表里加一行，加到几十行以后无法维护
- 规则表是**白名单**：没写到的组合就不发生任何事，玩家的组合大半无效
- 规则之间互相重叠时行为不确定（「长舌 ⇄ 吊死」和「吊死 ⇄ 不倒翁」同时成立时谁先算？）

## 2. 关键认知

**参考 Minecraft 的红石电路。**

红石块的逻辑只有「有电 / 没电」，中继器只有「充能 / 断电」，比较器只有「比较两个信号」。
**没有任何一条规则写着「红石块 + 中继器 + 比较器 = 永动机」。**
但你把这三个方块按正确的位置摆好，它就是个永动机——规则没变，涌现变了。

鬼工厂的鬼应该是一样的：

| 鬼 | 它自己的规则（全部） |
|---|---|
| 长舌鬼 | 每 2.0s 舌头伸出，试图抓住相邻格的目标；缩回时把目标拉近并推出 |
| 吊死鬼 | 挂上吊绳后自动伸展一格再收回，伸展时推开前方目标 |
| 不倒翁鬼 | 被移动时产 3 鬼能 |

**长舌鬼 + 吊死鬼 = 永动机**，是这三个规则在特定几何位置下自然叠出来的，不是被写下来的。

推论：

> 鬼的行为只描述「我自己做什么」，不描述「我和谁在一起会怎样」。
> 后者是玩家的发现，不是程序员的分支。

## 3. 端口标签的职责收窄

标签从「触发什么」降级为「能不能联动」。

```
长舌鬼.ACTION = GRAB       （长舌鬼能作用于「被抓住的东西」）
吊死鬼.RECEPTACLE = GRAB    （吊死鬼能被抓住）
→ 标签命中，允许建立连接
```

连上之后发生什么，**不由标签决定**，由物理求解算出来。

标签只在**玩家连线的那一刻**参与校验（不匹配就把线画红并拒绝），连上之后就不再介入。

完整配对表见 `GameDesign.md` §5.2。

## 4. 物理层的三步循环

每 tick（20 Hz）：

```
1. 提出意图    每只鬼按自己的 CD 与状态提出意图，互不知情
2. 合法性过滤  意图涉及的连接若标签不匹配，作废
3. 冲突消解    同一目标被多只鬼争抢 → priority → 距离 → 放置顺序
4. 执行        胜者执行，其余作废
```

**第 3 步是唯一的仲裁规则。** 所有「两只鬼凑一起会怎样」的答案都从这里长出来。

意图类型：

| 意图 | 产生者 | 含义 |
|---|---|---|
| `PULL` | 长舌鬼 | 抓住相邻格目标，拉向自己 |
| `EXTEND` | 吊死鬼 | 向目标方向伸展一格 |
| `RETRACT` | 吊死鬼 | 收回伸展 |
| `PUSH` | 长舌鬼 | 把抓住的目标推出去 |
| `SWAY` | 不倒翁鬼 | 被推动时的回摆反应 |
| `CONSUME` | 灶鬼 / 收容鬼 | 从输入缓冲取一件物料 |
| `PRODUCE` | 灶鬼 / 不倒翁鬼 / 贪食鬼 | 产出物料或鬼能 |
| `COLLECT` | 贪食鬼 / 细嚼鬼 | 从采集区取一件掉落物 |
| `TRANSFER` | 线鬼 | 沿路径送一件物料 |

## 5. 鬼的四大类

按工业化流程分：**运输 / 收集 / 产能 / 加工**（供品口另计为交付）。

**类别是描述性标签，不参与任何判定逻辑。** 两只运输鬼连上不会触发「运输加成」——它们只是各自按自己的规则跑，结果恰好落在分类描述的倾向里。

分类只服务两件事：

1. 给玩家读懂（拿到新鬼就知道它是干什么的）
2. 给关卡设计选教学点

## 6. 代码要怎么变

### 6.1 现在的形状（要改掉的）

```gdscript
# BoardRunner.gd 现状
func _tick_ghost(ghost: Node2D) -> void:
	match ghost.get_ghost_id():
		"LongTongue": _tick_long_tongue(ghost)
		"Stove":      _tick_stove(ghost)
		"Glutton", "FineChew": _tick_collector(ghost)
		"Fork":       _tick_fork(ghost)
		"Contain":    _tick_contain(ghost)
```

问题：加一只鬼要改核心逻辑；「两只鬼凑一起」的行为要么写进各自的分支（变成规则表），要么根本不发生。

### 6.2 目标形状

```
GhostData（数据层）
  category: transport / collect / produce / process / deliver
  action_tags / receptacle_tags   ← 只用于连线合法性
  priority: int                    ← 争抢裁决用
  footprint / appendages / cost / cd / buffer 容量 …

GhostBehavior（行为层，一份策略）
  LongTongueBehavior   → 提出 PULL / PUSH 意图
  HangedBehavior       → 提出 EXTEND / RETRACT 意图
  TumblerBehavior      → 响应 SWAY 意图
  StoveBehavior        → 提出 CONSUME / PRODUCE 意图
  GluttonBehavior      → 提出 COLLECT / PRODUCE 意图
  LineBehavior         → 提出 TRANSFER 意图

PhysicsSolver（物理层，核心，永远不改）
  1. 收集所有鬼的意图
  2. 标签合法性过滤
  3. 冲突消解（priority → 距离 → 放置顺序）
  4. 执行
```

**新增一只鬼 = 一个 .tres + 一个 Behavior 类，核心层零改动。**

### 6.3 迁移顺序（不破坏当前可演示版本）

| 阶段 | 做什么 | 风险 |
|---|---|---|
| 0 | 现状（已完成并可玩） | — |
| 1 | `GhostData` 加 `category` 与 `priority` 字段，不改行为 | 极低，纯数据 |
| 2 | 抽出 `GhostBehavior` 策略类，但先让 `BoardRunner` 仍按旧分支调用 | 低，行为不变 |
| 3 | 引入 `Intent` 与 `PhysicsSolver`，先只接管「争抢裁决」 | 中 |
| 4 | 所有鬼的行为迁移到 Intent 模型 | 中高 |
| 5 | 实现永动机等涌现案例并验证 | — |

**每阶段结束都要跑通既有 headless 测试**（当前 6 套共 438 项断言）。
