# 物理层设计说明

> 本文说明物理层的规则与实现约束。
> 正式条款见 `GameDesign.md` §8 与 `Ghosts.md`。

## 0. 版本沿革

| 版本 | 转向 | 结果 |
|---|---|---|
| v7~v8 | 形态 / 配方 / 共鸣规则表 / 供品交付 | 规则表白名单化，组合大半无效 |
| v9 | 改为物理层涌现（意图 → 统一结算），并砍掉采集 / 加工 / 垃圾 / 供品，收敛为单能量累计产出 | 涌现模型保留，资源层砍得过于激进 |
| **v10** | **恢复采集 / 加工 / 杂质 / 贡品交付，但保留涌现模型** | 现行玩法方案 |
| **v11** | **玩法冻结；表现层改为 3D 斜俯视 + 八向旋转相机** | 物理层零改动，新增相机 / 拾取 / 遮挡规范（见 §8） |
| **v12** | **按设计者裁决落地 C1~C6 / C8~C10；C7 待议** | 玩法局部解冻，但意图 / Solver / 推动链 / 三条红线不变（见 §4.4） |

**v10 的核心判断**：v9 砍掉采集与加工是对的（避免规则表膨胀），但把「一份资源两用」和「损耗」也一起砍掉，导致只剩一条资源线、没有取舍。**v10 把取舍加回来，但用涌现的方式加。**

**v11 的核心判断**：v10 的玩法方向不再折腾，改的是「玩家怎么看见它」。3D 化必须严格停在表现层，否则会连带把「以格为结算单位」「推动链」「单层网格」这些根基一起改掉。因此 §8 明确列出三条红线。

## 1. 为什么保留涌现模型〔v10 保留〕

原策划案（v8）的「三层共鸣结构 + 共鸣规则实例表」的问题：

- 每加一条共鸣，就要往规则表里加一行，加到几十行以后无法维护
- 规则表是**白名单**：没写到的组合就不发生任何事，玩家的组合大半无效
- 规则之间互相重叠时行为不确定

**参考 Minecraft 的红石电路。** 红石块的逻辑只有「有电 / 没电」，中继器只有「充能 / 断电」，比较器只有「比较两路信号」。**没有任何一条规则写着「红石块 + 中继器 = 永动机」**，但你把三个方块按正确的位置摆好，它就是个永动机。

所以：

> **鬼的行为只描述「我自己做什么」，不描述「我和谁在一起会怎样」。**
> 后者是玩家的发现，不是程序员的分支。

## 2. 端口标签的职责〔v10 保留〕

标签只回答一个问题：**这两个鬼之间允许建立连接吗？**

```
运输鬼.ACTION = HAUL       （运输鬼能搬运东西）
处理鬼.RECEPTACLE = HAUL   （处理鬼能收东西）
→ 标签命中，允许连接
```

连上之后发生什么，**不由标签决定**，由物理求解算出来。

标签只在**玩家连线的那一刻**参与校验（不匹配就把线画红并拒绝），连上之后就不再介入。

> 〔v11〕端口图标在 3D 里是面向相机的 Billboard，但标签校验逻辑与端口朝向语义完全不变；转到背面看不会改变「能不能连」。

## 3. 物理层的三步循环〔v10 保留〕

每 tick（20 Hz）：

```
1. 提出意图    每只鬼按自己的 CD 与状态提出意图
2. 合法性过滤  意图涉及的连接若标签不匹配，该意图作废
3. 冲突消解    同一目标被多只鬼争抢 → priority → 距离 → 放置顺序
4. 执行        胜者执行，其余作废
```

**第 3 步是唯一的仲裁规则。** 所有「两只鬼凑一起会怎样」的答案，都从这里长出来。

意图类型：

| 意图 | 产生者 | 含义 |
|---|---|---|
| `PRODUCE` | 生产鬼 | 产出鬼能并掉落在四邻随机空格 |
| `COLLECT` | 采集鬼 / 贪食鬼 | 从掉落物**四邻格之一**取走一件掉落物（v12） |
| `HAUL` | 运输鬼 | 把一件东西搬到目标端口 |
| `PROCESS` | 处理鬼 | 从输入缓冲取一件，加工成贡品 |
| `DELIVER` | 运输鬼 → 设施 | 送达 `BoardPort` 实例（交付口 / 仓库口），形态由 `accepted_form` 校验（v12） |
| `PUSH` / `PULL` | 推舌鬼 | 推动或拉拽相邻格目标 |
| `SWAY` | 守财鬼 / 吊死鬼 | 被推动时的回摆反应 |

## 4. v10 新增的三处裁决〔v10 保留〕

### 4.1 物理与格子如何共存

物理是连续的，格子是离散的。**裁决：以格为位移的最小结算单位。** 物理决定**谁动了谁**，格子决定**动到哪里停下**，动画负责把一格铺得顺。

这条同时解决了「采集鬼的 DFS 寻路」与「物理驱动」的对立：DFS 决定搜索顺序与步数，物理决定谁挡路、谁能被推动。

### 4.2 触发类型只是描述，不是判定

`自动 / 被动 / 检验后` 三种触发类型写在 `GhostData` 里，**只用于关卡设计选点与玩家读懂**，不参与任何 `if`。

- 自动触发的鬼自己按周期动
- 被动触发的鬼被推、被撞才动
- 检验后触发的鬼产出先落到待检状态，由设施检验后才计分

检验的执行者是**交付口**（`BoardPort` 的 `DELIVERY` 实例，设施，不是鬼），不合格品转杂质。这样「检验」有明确的落点，杂质也有了合法来源。

### 4.3 类别与触发类型都不进判定

**类型（生产 / 采集 / 运输 / 处理）不参与任何判定逻辑。** 两只运输鬼连上不会触发「运输加成」——它们只是各自按自己的规则跑，结果恰好落在分类描述的倾向里。

判定逻辑里不允许出现：

```gdscript
# 反面：match 分支硬编码，加一只鬼要改核心逻辑
func _tick_ghost(ghost: Node2D) -> void:
	match ghost.get_ghost_id():
		"Producer": _tick_producer(ghost)
		"Collector": _tick_collector(ghost)
```

> 〔v11〕示例代码里的 `Node2D` 在 3D 场景下对应 `Node3D`，但「不允许按鬼 id 硬编码分支」这条约束不变。

### 4.4 v12 裁决对物理层的影响〔v12 新增〕

**结论：`PhysicsSolver` 一行不改。** v12 的 9 条裁决全部落在数据层、关卡层或输入层，没有一条需要修改「收集意图 → 合法性过滤 → 冲突消解 → 执行」。

| 裁决 | 落在哪一层 | Solver 是否要改 |
|---|---|---|
| 放置后玩家一律不可拖、柔体只被机关推动 | 输入层（删掉玩家位移意图） | 否 —— 玩家拖动本来就不进 Solver |
| 相邻格拾取 | `COLLECT` 意图的可达性判定改用 `GridUtil.Neighbors4()` | 否 —— 仲裁顺序不变，只是目标格从「掉落物格」变成「四邻格」 |
| 输入区 / 输出区对应格子 | 意图的源 / 目标从抽象缓冲改成明确格 | 否 |
| 搜索区软上限 + 步进惩罚 | 只改 `search_step` 耗时 | 否 —— DFS 顺序与仲裁不变 |
| 空间预算 = 可放置区面积 | 关卡加载与放置校验 | 否 |
| 交互口做成 `BoardPort` 类 | 设施 / 数据层，`accepted_form` 由数据读 | 否 —— Solver 仍只按端口标签过滤，不认识形态 |
| 第 1 关交付鬼能、目标数重定 | 关卡数据 | 否 |
| 拆除绑 `Delete` | 输入 / UI 层 | 否 |

**三条红线（§8.2）继续有效**：Solver 不认识 3D、不用真实 3D 物理、不引入高度层。v12 新加的 `BoardPort` 与 `goal_form` 校验都在 Solver 之外。

## 5. 代码目标形态〔v10 保留〕

```
GhostData（数据层）
  category: produce / collect / transport / process   ← 描述性，不进判定
  trigger_type: auto / passive / inspected            ← 描述性，不进判定
  movable: rigid / soft
  action_tags / receptacle_tags   ← 只用于连线合法性
  priority: int                    ← 争抢裁决用
  footprint / appendages / cost / cd / buffers / search_area …
  model / model_height / port_facing                  ← v11：纯表现字段，不进判定
  BoardPort: port_kind / accepted_form / capacity     ← v12：设施配置，不进 Solver

GhostBehavior（行为层，一份策略）
  ProducerBehavior   → 提出 PRODUCE 意图
  CollectorBehavior  → 提出 COLLECT 意图（含 DFS 搜索）
  TransporterBehavior→ 提出 HAUL 意图
  ProcessorBehavior  → 提出 PROCESS 意图

PhysicsSolver（物理层，核心，永远不改）
  1. 收集所有鬼的意图
  2. 标签合法性过滤
  3. 冲突消解（priority → 距离 → 放置顺序）
  4. 执行
```

**新增一只鬼 = 一个 .tres + 一个 Behavior 类，核心层零改动。**

**PhysicsSolver 在 v11 中一行不改。** 它只认识 `(col, row)` 整数格，不认识相机、模型高度、世界坐标或遮挡。

## 6. 迁移顺序（保护现有可运行部分）〔v10 保留 + v11 插入 3D 阶段〕

| 阶段 | 做什么 | 风险 |
|---|---|---|
| 0 | 现状（Autoloads / Common / UI 已可用，玩法层已删除待重做） | — |
| 1 | 重建 `GhostData` / `LevelData` / `Board` 骨架，跑通「放鬼 → 运行 → 掉落」 | 低 |
| **1.5**〔v11〕 | **搭 3D 表现骨架**：`GridFloor3D` + 正交斜俯视 `CameraRig` + `Picker3D`（射线 → 地面 → 格）。**先验证「旋转相机后同一布局判定完全一致」**，再继续 | 中 |
| 2 | `GhostData` 加 `category` / `trigger_type` / `movable` / `priority` 字段，不改行为 | 极低 |
| 3 | 引入 Intent 与 Solver，先只接管争抢裁决 | 中 |
| 4 | 所有鬼的行为迁移到 Intent 模型 | 中高 |
| 5 | 实现推动链、永动机等涌现案例并验证 | — |
| **6**〔v11〕 | **3D 表现收尾**：模型 / 状态 Billboard / 连线管 / 范围框 / 描边 / X-Ray / 教程聚光灯投影 / 罗盘与相机控件 | 低（纯表现） |

每阶段结束都要跑通既有 headless 测试（当前 `SaveManagerRoundTrip` / `UiFlowTest` / `UiPolishTest`）。

**v12 前置**：阶段 1 重建 `GhostData` / `LevelData` / `Board` 骨架时，**直接按裁决后的结构建**——交互口是 `BoardPort` 类、关卡带 `placeable_cells` / `goal_form`、拾取走四邻格、搜索区带软上限惩罚、拆除绑 `Delete`、已放置的鬼不接玩家拖拽。不要先按 v10 建好再返工。

**v11 的阶段安排原则**：逻辑网格与意图结算先在 headless 下跑通，**相机不是玩法层的前置依赖**。阶段 1.5 插入得早，是为了尽早暴露「3D 拾取把格坐标算错」这类会污染全部后续阶段的问题；阶段 6 放最后，是因为它全是表现，不影响玩法正确性。

新增 headless 回归项：

- 八个 `yaw` 档下，同一份布局的 tick 结果（掉落、拾取、缓冲、故障、计分）逐帧一致
- 相机旋转 / 缩放 / 平移 / X-Ray 不产生任何意图、不触发 tick、不改写状态
- 暂停状态下仍可自由转视角，恢复后状态与暂停前一致

## 8. v11：3D 表现层转向〔v11 新增〕

### 8.1 为什么要改

v10 的玩法是「在格子上摆机器、看它们自己跑起来」，2D 平面表现够用，但：

- 机器、线路、掉落物、杂质全挤在一个平面上，布局稍复杂就难读
- 「推动链」「柔体让位」这些涌现行为是空间关系，固定视角下看不清谁挤了谁
- 立体厂区更贴合「阴间工厂」的世界观

**改的是可读性，不是玩法。** 八向旋转让玩家主动找能看清的角度，X-Ray 让被挡住的线路仍然可布。

### 8.2 三条红线

| 红线 | 说明 |
|---|---|
| **Solver 不认识 3D** | 意图、仲裁、推动链、DFS 全部在 `(col, row)` 上算，禁止把 `Camera3D`、模型高度、遮挡状态传进 Solver |
| **不用真实 3D 物理** | 不引入 `RigidBody3D`、重力、真实碰撞体积；推动链仍以格结算，动画负责把一格铺顺（`GameDesign.md` §8.5） |
| **不引入高度层** | 没有多层堆叠、没有跨层输送、没有「楼上的鬼」；模型高度只影响观感与遮挡 |

这三条任一被打破，v10 的「以格为位移最小结算单位」与「推动链」就不再成立，等于换了一个游戏。

### 8.3 3D 下的物理表达

| 项 | v10 | v11 |
|---|---|---|
| 位移结算 | 一格 | 一格（不变） |
| 推力方向 | 逻辑四邻 | 世界四邻（同一套格坐标，不随相机变） |
| 动画 | 2D 平面补间 | 世界 `(x, z)` 平面补间，可加 `y` 弹跳；弹跳只是动画，不改落点 |
| 遮挡 | 无 | 被挡住的鬼照常参与全部结算，只是不能点选 |
| 相机 | 固定 | 八向旋转，与 tick 完全解耦 |

### 8.4 新增的只是「看」和「点」

- **看**：正交相机、地台、模型、状态 Billboard、连线管、范围框、描边、X-Ray、罗盘
- **点**：射线 → 地面平面求交 → `WorldToGrid` → 查格占用表；实体精确点选用 3D 碰撞体射线
- 这两层都不产生意图、不改写状态、不进 SignalBus 的玩法信号；新增的 `CameraYawChanged` / `XRayModeChanged` 等只驱动表现

## 9. 3D 化不改的东西〔v11 新增，核对清单〕

开工前逐条核对，任何一条被改动都说明偏离了 v11 方向：

- [ ] 鬼清单：具名鬼的行为、端口、造价、占位不改；设施改为统一的 `BoardPort` 类（第 1 关 1 个、第 2 / 3 关 2 个）〔v12 已定〕
- [ ] 三条描述轴、状态机、故障条件与手动恢复
- [ ] 端口标签校验、连线折线占格、空间不足拒绝
- [ ] 鬼能经济：一份两用、仓库、贡品、25% 损耗、再处理全额回收
- [ ] 掉落：四邻均匀随机、四邻无空格进缓冲、缓冲满故障
- [ ] 采集：**DFS 顺序不变**，步进带软上限惩罚，拾取在相邻格完成、背压不变〔v12 已定〕
- [ ] 意图类型表、三步循环、冲突消解 `priority → 距离 → 放置顺序`
- [ ] 推动链、刚体止点、柔体让位、五类代价
- [ ] 三关**时限 / 障碍 / 评分三轴 / 元进度**不变；目标数与空间预算定义按 v12 重定〔v12 已定〕
- [ ] 全部数值（tick 20 Hz、周期、速度、缓冲、损耗率、开局鬼能）
- [ ] 教程五件事、秘书鬼设定、存档段结构、UI 信息架构

判断偏离的标准是 §8.2 的三条红线。

**允许改动的只有**：坐标单位措辞（px → 世界单位）、节点类型（2D → 3D）、`GhostData` / `LevelData` 新增纯表现字段、`GridUtil` 增量加 3D 换算、教程聚光灯实现、界面新增相机控件、新增表现层信号、`ExportSettings` 新增相机参数。
